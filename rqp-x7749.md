# Writeup — Red Queen Protocol

OS: Linux
Difficulty: Easy
Date: October 2026

reverse engineering means taking a compiled program and working out what it does without having the source code. the compiler threw the readable code away and left machine instructions, you work backwards from those

this room gives you four binaries in ~/recovered_terminals. each one asks for a password and prints a flag if you get it right, and each one hides that password in a different way, so you cannot clear the whole thing with a single tool. that is the actual lesson here. everything is guided, nothing requires prior experience, you just need to be comfortable in a terminal

## Level 1 - simple analysis

before touching a binary, find out what it is

cd ~/recovered_terminals
file ./hive_terminal

ELF 64-bit, PIE, dynamically linked, not stripped. ELF is just the Linux equivalent of an .exe, and not stripped means function names are still in there, which makes life easier later

checksec --file=hive_terminal

full RELRO, canary, NX, PIE. these are anti exploitation protections and none of them affects this room, but getting into the habit of checking costs two seconds

now the actual question: does the binary carry readable text around? when you write a string in C, something like a password or an error message, the compiler copies those exact bytes into a section called .rodata, read only data. they stay there in plain ASCII, nobody encrypts them for you. strings scans the file and prints every run of printable characters it finds

strings -n 8 ./hive_terminal

the -n 8 just means ignore anything shorter than 8 characters, which cuts most of the noise. scrolling through libc symbols and section names, two lines obviously do not belong: UMBRELLA-7749, and the flag right under it. the first one is what the prompt wants

./hive_terminal

type UMBRELLA-7749 at the Employee ID prompt and the door opens

## Level 2 - static analysis

run strings on keypad and there is nothing usable. that tells you something: the password is not stored as text, it gets built while the program runs. so you need to read the logic, not the data

static analysis means reading the code without executing it. the tool is Ghidra, which disassembles the binary and then reconstructs something close to C out of the assembly. it is not the original source, it is a reconstruction, but it is readable

open Ghidra from the Desktop, it takes a minute or two to start. the project already contains keypad, double click it, accept the default analysis options and wait for the progress bar at the bottom right to finish

on the left there is a panel called Symbol Tree. expand Functions, double click main, and the decompiled C shows up in the Decompiler panel on the right

main compares your input with strcmp, and one of the two things it compares comes out of a function called decode_code. double click that name to follow it

inside, the decompiler shows a 26 byte array filled one element at a time, then this loop

  lVar1 = 0;
  do {
    *(byte *)(param_1 + lVar1) = local_38[lVar1] ^ 0x5a;
    lVar1 = lVar1 + 1;
  } while (lVar1 != 0x1a);

the caret is XOR, 0x5a is the key, 0x1a is 26 in decimal so the loop covers the whole array. XOR has a property that makes this trivial: if you XOR something twice with the same key you get the original back. encrypting and decrypting are literally the same operation, so you just redo it

copy the array values out of Ghidra and run

python3 -c "print(''.join(chr(b^0x5a) for b in [0xe,0x12,0x17,0x21,0x3e,0x12,0x1f,8,0x1f,5,0xd,0x1b,9,5,0x1b,0x14,5,0x13,0x14,0x19,0x13,0x1e,0x1f,0x14,0xe,0x27]))"

THM{THERE_WAS_AN_INCIDENT}

## Level 3 - dynamic analysis

override does the same trick but the key changes at every character instead of staying fixed. you could still rebuild it by hand from Ghidra, it is just boring and easy to get wrong

dynamic analysis is the shortcut: run the program and watch it work. a debugger lets you freeze execution at any single instruction and look at what is in memory and in the CPU registers at that exact moment. the tool is gdb, with the GEF plugin on top which prints everything useful automatically

the key idea is picking where to freeze. the comparison goes through strcmp, and on x86-64 the first two arguments of a function always travel in the registers rdi and rsi. so at the instant strcmp is called, rdi holds what you typed and rsi holds what the program expected. that second one is the answer

gdb ./override
disassemble main

look for the line calling strcmp@plt. here it is at main+162. the binary is PIE, meaning it normally loads at a random address, but gdb disables that randomisation so the base is always 0x555555554000 and the full address is predictable

b *0x000055555555531e
run

b sets the breakpoint, run starts the program. type anything at the prompt, execution stops right before the compare and GEF already prints the guessed arguments at the bottom. if it does not, read the register yourself

x/s $rsi

x/s means print the string at this address

## Level 4 - symbolic execution

memory_unlock is the one that breaks the pattern. open validate in Ghidra and there is no stored password anywhere, not in plaintext, not encoded. the function just runs your input through a chain of checks and only one combination passes all of them. there is nothing to extract because nothing was ever written down

so instead of giving the program concrete characters, you give it unknowns. angr executes the binary with symbolic bytes, think of them as x, y, z, and every if it hits becomes an equation about those unknowns. once it reaches the success path it hands the whole system to a solver called Z3 and asks which concrete values make all the equations true at the same time. it is algebra, not guessing

the room ships task5_solve.py already written: one symbolic byte per expected character, explore until the success message appears, throw away any execution path that ends in failure. worth reading before running it, it is short

python3 task5_solve.py

it takes a couple of minutes because the solver is doing real work

THM{I_REMEMBER_EVERYTHING}

there is a second script, task5_underconstrain.py, same binary with fewer constraints. run it a few times and it returns a different valid answer every time, almost none of them the one you want. good reminder that a solver gives you something that satisfies the equations you wrote, not the thing you had in your head
