# Writeup — Red Queen Protocol

OS: Linux
Difficulty: Easy
Date: October 2026

easy room, four binaries in ~/recovered_terminals and every one of them hides its key in a different way. nothing here is hard, the point is that each level pushes you towards a different technique instead of letting you bruteforce your way through with the same tool

## Level 1 - simple analysis

first thing, see what you are dealing with

cd ~/recovered_terminals
file ./hive_terminal

ELF 64-bit, PIE, dynamically linked, not stripped. checksec gives full RELRO, canary, NX and PIE, none of it matters for this room but it is a good habit

string literals written in C end up in .rodata verbatim, so if the author hardcoded the password it is sitting there in plain ASCII

strings -n 8 ./hive_terminal

two lines clearly do not belong among the libc noise: UMBRELLA-7749 and the flag itself. the first one is what the Employee ID prompt wants

THM{WELCOME_TO_THE_HIVE}

## Level 2 - static analysis

strings on keypad gives nothing, so the value is built at runtime rather than stored. open it in Ghidra, default analysis, then Symbol Tree, Functions, main

main validates with strcmp and one of the two operands comes out of decode_code. that function assigns a 26 byte array one element at a time and then runs this

  lVar1 = 0;
  do {
    *(byte *)(param_1 + lVar1) = local_38[lVar1] ^ 0x5a;
    lVar1 = lVar1 + 1;
  } while (lVar1 != 0x1a);

single byte XOR with a fixed key. XOR is symmetric so applying the same operation to the array gives back the plaintext, no need to invert anything

python3 -c "print(''.join(chr(b^0x5a) for b in [0xe,0x12,0x17,0x21,0x3e,0x12,0x1f,8,0x1f,5,0xd,0x1b,9,5,0x1b,0x14,5,0x13,0x14,0x19,0x13,0x1e,0x1f,0x14,0xe,0x27]))"

THM{THERE_WAS_AN_INCIDENT}

## Level 3 - dynamic analysis

override builds its key incrementally, a different value for every character, so pulling the array out and decoding it statically would mean reimplementing the whole schedule by hand. easier to let the binary do the work and watch

the comparison still goes through strcmp and at that instruction both strings are already loaded, my input in rdi and the expected one in rsi. so the breakpoint goes on the call itself

gdb ./override
disassemble main

the call to strcmp@plt sits at main+162. gdb kills ASLR on its own so with PIE the base stays at 0x555555554000 and the absolute address is predictable

b *0x000055555555531e
run

type whatever at the prompt, execution stops before the compare and GEF already prints the guessed arguments. rsi is the one you want

x/s $rsi

THM{LOCKDOWN_PROTOCOLS_INITIATED}

## Level 4 - symbolic execution

memory_unlock is the odd one. validate does not compare against a stored value at all, it pushes the input through a chain of checks and exactly one combination survives all of them. there is nothing to extract because the answer was never written anywhere in the first place

so you hand the program unknowns instead of guesses. angr runs it with symbolic bytes, turns every branch into a constraint and then asks Z3 which concrete values satisfy the whole system at once. the room ships task5_solve.py already set up, one symbolic byte per expected character, explore until the success output is reached, discard every state that falls into the failure path

python3 task5_solve.py

couple of minutes, the solver is actually working

THM{I_REMEMBER_EVERYTHING}

task5_underconstrain.py is worth a look too, same binary with looser constraints. it returns a different valid answer on every run and basically none of them is the one you want, which is a decent reminder that the solver gives you something that fits the equations, not the thing you had in mind
